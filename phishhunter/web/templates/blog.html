PHISH-HUNTER-K4 · ENGINEERING JOURNAL

Building a defensive analysis platform from the evidence up.

This project is a practical engineering effort to make phishing, malware, network and threat-intelligence analysis easier to understand, reproduce and document. The goal is not to hide the investigation behind a polished score; the goal is to keep the evidence visible.

ARCHITECTURE

Why Phish-Hunter is evidence-first

Security analysis is only useful when another analyst can understand why a conclusion was reached. K4 therefore treats the original artifact, normalized observations, extracted indicators and analyst findings as separate pieces of evidence.

A URL investigation can begin with a target, continue through host and redirect observations, extract domains and IP indicators, and finish with a report. A file investigation can record hashes, file type, strings, metadata and static signals without executing the sample. A PCAP investigation can preserve flow and endpoint metadata so the network story remains reviewable.

This design makes the platform useful for learning as well as operational work: an analyst can inspect the evidence behind a result instead of simply accepting a number.

SAFE ANALYSIS

Designing a local-first upload and analysis pipeline

Uploaded artifacts are treated as security-sensitive evidence. The application validates uploads, limits their size, identifies supported content and keeps analysis inside the application boundary. Static file analysis does not require executing a submitted sample on the web server.

The pipeline is intentionally staged: intake, validation, normalization, analysis, enrichment, correlation and reporting. That separation makes it easier to replace an analyzer, add a new evidence source or run the same workflow from an API endpoint.

For production deployments, the project can be extended with isolated analysis workers or dedicated malware sandboxes. The web application itself should never be treated as a malware execution environment.

NETWORK FORENSICS

Turning PCAP metadata into an investigation timeline

Packet captures can contain an enormous amount of information. K4 focuses the first pass on useful defensive metadata: conversations, endpoints, ports, protocols, timestamps and suspicious findings.

That first pass is designed to answer practical questions: Which systems communicated? Which services were contacted? When did the activity happen? Which indicators should be pivoted into a case or threat-intelligence lookup?

The result can then feed IOC extraction, graph relationships and reporting. This keeps the workflow understandable while leaving room for deeper protocol-specific analysis.

THREAT INTELLIGENCE

External enrichment should add context, not replace evidence

Threat-intelligence providers can add useful context to an investigation, but an external reputation result is not the same thing as local evidence. K4 therefore treats enrichment as an optional second layer.

When credentials are configured, a connector can enrich an observed URL, domain, IP, hash or other indicator. When credentials are unavailable, the local workflow should still be useful. This makes the platform easier to self-host and easier to use for education.

The same principle applies to reports: a report should distinguish what K4 observed locally from what an external provider returned.

OPEN SOURCE

Why the project is free and open

Cybersecurity knowledge grows when people can inspect systems, reproduce workflows and learn from real implementation details. K4 is being built as a free, open-source project so students, researchers and defenders can study the architecture instead of treating the platform as a black box.

Self-hosting also gives organizations more control over where evidence is stored. The project can be adapted for a lab, a personal research environment or an authorized internal defensive workflow.

Open source does not remove the need for security discipline. Deployments still need strong secrets, appropriate access controls, isolated malware execution and responsible handling of sensitive artifacts.

ROADMAP

Where the platform can grow next

The architecture is designed to grow beyond the current web workflows. Future work can include stronger background job orchestration, richer case evidence, session and device management, MFA, PostgreSQL production profiles, more connectors, deeper PCAP processing and isolated sandbox workers.

The important constraint is that new features should remain connected to the investigation model: evidence enters, analysis produces observations, indicators are correlated, cases document decisions and reports preserve the result.

That gives the project a consistent direction even as the number of analyzers and integrations grows.
